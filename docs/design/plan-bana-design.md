## Problem Statement

A friend group wants to go out on Saturday. The chat fills with "kuch bhi chalega", "budget 800 max", "veg hai main", "sat raat free hu", "comedy?" and nobody decides. The search is easy; the **agreement** is the hard part. The Swiggy MCP builds we found are single-user (one person searching). Going out is a group decision.

Goal of this project: a demo that gets the builder an internship through Swiggy Builders Club (demo video + repo emailed to builders@swiggy.in).

## What Makes This Cool

- **Chaos → plan.** The bot reads the actual messy Hinglish group chat and says "Samjha: Sat raat, 4 log, ₹800/head, 1 veg, comedy". It asks one button question only for what's missing, then drops up to 3 real plans.
- **Real, bookable inventory.** Each plan is either a real Swiggy Scenes show + a real Dineout FREE table near the venue, timed after the show ends, or a dinner-only FREE table when no show fits. Every venue, show, slot and price on a card comes from a Swiggy response, not the model's imagination; estimates are marked "~".
- **Per-person proof.** Each plan card shows "Rohan veg ✓ · Priya ≤₹800 ✓ · Aman Sat ✓".
- **Flake-proof table.** Vote → ticket RSVP → the table is sized to who actually confirmed.
- **Gap in the market.** Web search on 2026-09-29/30 found no public project using Swiggy Scenes. The queries were "Swiggy MCP Dineout Scenes project github" and "AI group outing planner Telegram bot". The nearest builds are a VideoSDK voice agent (Dineout only) and a PHP client wrapper. District's only group feature found was Splitpay (indianretailer.com). A student District product teardown on nextleap.app (found in the same 2026-09-30 search) suggests "invite friends to a shared planning workspace and vote on activities" as a missing feature. The pitch: "District doesn't have this; here's Swiggy doing it."

## Constraints

- **Money-moving actions stay locked.** `DRY_RUN=1` stays until the builder explicitly says otherwise.
  - `book_table` is already in `PLACE_ORDER_TOOLS` (`maa/swiggy.py:21`), so `SwiggySession.call("book_table")` raises `OrderBlocked`.
  - The only path is `SwiggySession.place_order("book_table", …)`, which raises `OrderBlocked` unless `DRY_RUN == "0"`.
- **Scenes tickets are prepaid UPI** (`create_event_cart` → `place_event_order`). The bot never buys tickets. It names/links the show, and each friend books their own in the Swiggy app.
- **Dineout `book_table` works directly only for FREE deals.** PAID deals need a cart + UPI, so they're out of scope.
- **No `cancel_booking` tool exists.** A wrong booking has to be cancelled by hand in the Swiggy app, so booking is always a deliberate human tap, placed after tickets (see "Order of commitment").
- **`discover_events` returns nothing live.** Use `search_events` by genre/keyword. `list_event_shows` needs the `venueId` from `get_event_details`.
- **Dineout search needs lat/lng.**
- **Telegram Bot API has no chat-history call.** The bot sees group messages only after it joins, and only with privacy mode off. `/setprivacy` → Disable takes effect only after the bot is removed and re-added to the group.
- **Stack:** Python 3 asyncio, MCP SDK over streamable HTTP, Gemini `gemini-3.8-flash` (google-genai, manual function calling), SQLite WAL, Telegram long polling, Windows + Git Bash. Telegram long polling needs no public URL, so no ngrok.
- **Timeline:** ~1–2 weeks of part-time build, with a cut line (below).

## Premises (agreed)

1. The hard part is group agreement, not search. The value is chat chaos → one decided plan.
2. Every event/show/venue/restaurant/deal/slot ID in a plan must appear in a Swiggy tool response from the same planning run. Code rejects anything else. The one exception is the Book-time re-fetch (see Book). If no event fits, the bot offers dinner-only plans.
3. The bot books only FREE Dineout tables, only after the organizer taps Book, only after re-checking the slot, and only behind DRY_RUN. Event tickets are linked, not bought.
4. Reuse the Maa ka Swiggy infra:
   - `maa/auth.py`, `maa/swiggy.py` (session + DRY_RUN lock + `embedded_json`)
   - `maa/store.py` (jobs with leases, per-`family_id` serial claim, `run_at` timers, settings)
   - `maa/telegram.py`, `maa/gemini.py`
   - the draft `maa/plan.py` planner + `validate_plans`

   WhatsApp, Sarvam and Instamart are not on the Plan Bana path.
5. Each group sets its area by dropping a Telegram location pin. It's stored per chat and changed only via `/area` (see Rules → Location).
6. The deliverable is a 60–90 s demo video + the GitHub repo, emailed to builders@swiggy.in. There's no public deploy.

## Approaches Considered

- **A: One-message planner** (`/plan sat raat 4 log comedy + pizza` → 3 plans → vote → Book). Rejected: it loses the chaos-to-plan moment and looks like "ChatGPT + Swiggy search".
- **B: Chaos-to-plan full loop.** Chosen.
- **C: Ambient listener** (the bot jumps in when it detects planning talk, no command). Rejected: false triggers and token cost, and a chatty bot gets kicked from groups.

## Recommended Approach: B — Chaos-to-plan full loop

### Flow

```
  bot added to group ─► one-time notice: "Main /plan ke liye pichle 24 ghante ki chat padhta hu. Plan ki details 7 din baad delete."
  every human text message ─► chat_messages buffer
        ▼
  /plan (sender ─► organizer of this round; open-round rule below)
        │  no pin ─► WAITING_PIN: "📍 Location pin bhejo" ─► organizer's pin arrives ─► resumes this round automatically
        ▼
  EXTRACTING (Gemini, one call, JSON-schema output of per-message statements) ─► code reduces to Constraints
        ▼
  CONFIRMING: "Samjha: Sat raat, 4 log, ₹800/head, 1 veg, comedy"   [✅ Sahi hai] [✏️ Badlo]
        │  gaps ─► one button question for the top gap; remaining gaps take defaults
        │  Badlo ─► organizer replies to that message in text ─► re-extract with the correction appended
        ▼
  PLANNING (progress message edited per stage: "🎭 shows dhoondh raha hu… 🍽 tables check…")
        │  planner tool loop on Constraints ─► propose_plans (IDs only) ─► CODE CHECKS per plan ─► 1 retry with failure reasons
        ▼
  VOTING: N plan cards (N = plans that passed, 0–3), per-person ✓/?/✗ + timeline, numbers from Swiggy data   [1️⃣]…[N]
        │  0 passed ─► "Kuch fit nahi hua: <top reasons>. Budget/area/din badlo?" round → CANCELLED
        ▼  lock rule
  RSVP: "Plan 2 locked 🎉 🎟 Tickets pehle: each person books here → <event>. Ticket liya / le raha hu?"
        │  [🙋 Main aa raha hu] [❌ Skip]   deadline 30 min; timer job ─► BOOK_PENDING + prompt organizer (never books)
        │  organizer may tap [Book now] earlier
        ▼
  BOOK_PENDING (organizer only): "Table for 3 at 10:00, <restaurant>? ⚠️ Swiggy can't auto-cancel tables."  [✅ Book] [❌ Cancel]
        │  Book tap ─► job: re-fetch list_event_shows + get_available_slots
        │    show gone ─► "Show ab list nahi hai. Sirf table?" [Table only] [Cancel]  (explicit organizer tap, stays BOOK_PENDING)
        │    slot gone ─► offer the nearest FREE slot that passes the same checks; organizer taps Book again (stays BOOK_PENDING)
        │  CAS BOOK_PENDING→BOOKING ─► place_order("book_table") ─► OrderBlocked (DRY_RUN) ─► TEST_ONLY "🧪 would book table for 3"
        ▼
  Final card: show time, table time, restaurant, party size, ticket pointer
```

### Rules

**Chat buffer**
- Stored: human text messages only. Not stored: bots, `/commands`, non-text, service messages.
- Edited messages update their row.
- Purge on every insert: rows older than 24 h are deleted, and at most 50 rows are kept per chat.
- `/status` shows the buffered message count (setup check before recording).

**Retention**
- Round data (Constraints, statements, votes, RSVPs, plan cards) is deleted 7 days after the round reaches a terminal state.
- The purge runs lazily on each `/plan`, so it survives the sweeper being cut.

**Location**
- Only the organizer's pin unblocks WAITING_PIN.
- `/area` followed by the same person's pin replaces the stored area.
- Any other location share is ignored.

**Extraction**
- Input: the buffer (message_id, sender, IST timestamp, text) plus "now" in IST.
- The model outputs **statements** only: `[{message_id, field, value}]`.
  - Fields: `date_ok` (a date the sender can do), `date_no`, `time_window`, `budget`, `veg`, `genre`, `not_coming`, `headcount`.
  - `user_id` and timestamp come from the buffer row for `message_id`. Statements citing unknown message_ids are dropped, and names always come from the buffer.
- Time words map to fixed windows: raat 19:00–23:30, shaam 17:00–20:00, dopahar 12:00–16:00. "Sat" = the coming Saturday (today if it's Saturday).
- **Code reduces statements to Constraints:**
  - **Per person:** the latest statement per field wins. `available[date]` = ✓ if `date_ok` covers it, ✗ if `date_no` or `not_coming` does, ? otherwise.
  - **Date:** the date with the most ✓. A tie goes to gaps.
  - **Time window:** the intersection of stated windows. If the intersection is empty, it goes to gaps.
  - **Budget:** the minimum stated budget.
  - **Genre:** the most-mentioned. On a tie, both genres are searched and plans may mix them.
  - **Headcount:** the larger of the validated people count and the largest stated `headcount`. The card says "4 log (3 chat mein)" when they differ.
- **Gaps and defaults:**
  - Priority: date > time_window > budget > genre > headcount. The one question asks the top gap.
  - Buttons per gap:
    - date: the next 3 days.
    - time: Shaam / Raat.
    - budget: ₹500 / ₹800 / ₹1200 / No limit.
    - genre: Comedy / Music / Kuch bhi.
    - headcount: 2 / 3 / 4 / 5+.
  - The remaining gaps take defaults: raat, no budget cap (budget ✓ shows ?), genre comedy + music, headcount = people count.

**Plan data and code checks**
- `propose_plans` carries IDs only: eventId, showId, venueId, restaurantId, itemId, slotId, reservationTime. Model-written text is display flavour and never feeds a check or a number on the card.
- `checks.py` parses the facts from the tool responses, keyed by those IDs: show start/duration/price, venue coords, cost_for_two, distance, veg flag, cuisines.
- It returns per-plan pass/fail with reasons. This replaces `validate_plans`' raise-on-first-error. Passing plans are kept, and the reasons feed the retry prompt and the 0-plan message.
- Checks per plan:
  1. Every ID is in the run's tool corpus, the showId belongs to the eventId, and the itemId is a `[FREE]` deal for that restaurant.
  2. The table time is inside `time_window` on `date`. For event plans, the show is on `date` and starts inside `time_window`.
  3. **Event plans:**
     - Dineout is searched at the venue's coords when Swiggy returns them, so distance is "known" only then.
     - Known distance > 5 km → fail.
     - Table time ≥ show end + gap. The gap is 20 min when the distance is known (≤ 5 km), and 45 min when it is unknown.
     - Show end = start + duration, or start + 90 min labelled "~".
  4. **Budget:**
     - Per head = ticket price (if known) + cost_for_two / 2. The group limit is the minimum stated budget.
     - Unknown ticket price → the card says "+ ticket".
     - Unknown cost_for_two → the plan passes, with every budget ✓ shown as ?.
  5. **Veg:** "veg-friendly" means veg options are available (not pure-veg).
     - A Swiggy veg flag, if present, decides.
     - Otherwise the plan fails only if every cuisine tag is in {Seafood, Kebabs, Barbecue, Steak, Meat}.
     - A "pure veg" statement requires the pure-veg flag; without the flag it shows ?.
- **Dinner-only plans:**
  - Trigger: no show passes check 2's show test, or no event plan passes all checks.
  - They are searched around the group's pin, may mix with event plans, skip check 3, and have no ticket step (lock → RSVP).

**Voting**
- Eligible = the organizer + validated people. Others get a toast: "Pehle chat mein bolo, phir vote". **Superseded by design DR4: any group member may vote/RSVP.**
- One vote per person; re-tapping moves the vote. The tally edits the card live.
- A plan locks when it has votes from more than half of the eligible voters, or when the organizer taps [🔒 Lock] on the current leader (≥1 vote). On a tie, the organizer's Lock tap picks among the tied plans.

**RSVP**
- Eligible = the same set as voters. Taps can be toggled until the organizer taps Book.
- The organizer is auto-included.
- Party size = confirmed count. Below 2 → no Book offered: "Sirf tum? Plan cancel ya dobara /plan".
- If the deal has a max party size (probe) and the count exceeds it → offer booking at the max, or cancel.

**Order of commitment**
- Tickets come before the table. The RSVP asks people to book their ticket first.
- The Book confirmation carries the no-auto-cancel warning.
- The Book re-check confirms the show is still listed (show-gone branch in Flow).

**Open round on a new /plan**
- The prompt goes to the sender of the new `/plan`.
- If the sender is the open round's organizer, or the round has been idle > 30 min, they get "Purana plan band karke naya?" [Haan] [Nahi].
- Otherwise they get a toast: "Ek plan chal raha hai (organizer: X)".
- Rounds idle > 6 h are treated as EXPIRED at this check, even without the sweeper.

### States

`WAITING_PIN → EXTRACTING → CONFIRMING (⇄ gap question / Badlo re-extract) → PLANNING → VOTING → RSVP → BOOK_PENDING (⇄ show-gone / alternate-slot offers) → BOOKING → {BOOKED | TEST_ONLY | FAILED | NEEDS_REVIEW}`

Also: `CANCELLED` (organizer cancel, 0 plans, party < 2) and `EXPIRED`.

- All transitions are compare-and-set, like `set_draft_state`.
- **BOOKING is set by compare-and-set before `place_order()`.** A booking job reclaimed after a lease expiry (`reclaim_expired`, 120 s) that finds the round already in BOOKING moves it to NEEDS_REVIEW and never calls `book_table` again.

Only the organizer may tap: Sahi hai, Badlo, gap question, Lock, Book now, Book, Table only, Cancel. Button payloads carry `round_id`, and a tap on a closed round gets a "yeh plan band ho gaya" toast.

### Concurrency

- **Inline (the poller does it and answers the callback in <1 s):**
  - Buffer inserts.
  - Vote and RSVP taps (one compare-and-set SQL write + message edit).
- **Queued as jobs on the existing queue with `family_id = "tg:<chat_id>"`:** extraction, planning, the RSVP deadline timer (`run_at`), and booking. Jobs for one group run one at a time; different groups run in parallel.
- Organizer-only taps that start work (Sahi hai, Book) are answered inline with "Working on it…" and then queued.

### Planner changes and latency

**The planner on Constraints:**
- It has **no `ask_group` tool**; all questions happen in CONFIRMING.
- Its system prompt is rewritten around Constraints and IDs-only `propose_plans`.
- It runs one `search_restaurants` per venue, not per plan.

**Call caps and timing:**
- Call caps: 20 tool calls per attempt, 30 per job. The retry gets what remains of the job budget. The probe (step 1) confirms or adjusts these.
- **New work:** tool calls from one model turn run concurrently. The current loop awaits them one by one (`maa/plan.py:229-243`).
- Hard deadline of 90 s per planning job. On timeout, the bot shows whatever passed the checks.
- The 60 s target is measured in the probe.

### Code layout

- New package `plan_bana/`: `buffer.py`, `extract.py`, `checks.py`, `rounds.py`, `bot.py`. Move `maa/plan.py` → `plan_bana/planner.py`.
- Import shared infra from `maa/`.
- Store: new tables `chat_messages`, `plan_rounds`, `statements`, `votes`, `rsvps`, `group_settings(chat_id, lat, lng, area)`.
- `scripts/serve_plan.py` runs the Telegram poller + worker.
- The Gemini planner is read-only and never gets booking tools. Booking is code-only via `place_order()`.
- A network error or timeout on `book_table` → NEEDS_REVIEW with no retry.

## Success Criteria

- On the scripted demo chat (4 people, ~10 messy messages), `/plan` gives a correct "Samjha" line with ≤1 follow-up question, then 3 plans that pass all checks, in under 60 s.
- In general: every shown plan passes checks 1–5, with zero invented IDs. Fewer than 3 plans is fine when fewer pass, and 0 plans gives the "kuch fit nahi hua" message.
- Voting, RSVP and organizer Book work end-to-end. Book shows TEST_ONLY with party size = confirmed count.
- Stale or foreign taps are rejected, non-organizers can't Book, and a second `/plan` doesn't corrupt the open round.
- Tests with fakes (like the current 155-test suite) cover: buffer rules, extraction reduction (unknown message_id drop, every conflict rule, gap defaults), every code check, lock/RSVP rules, the state machine, callback auth, the BOOKING reclaim guard and DRY_RUN on `book_table`.

### R3-1 — feasibility

**Problem**

> Check 3 says 'Dineout is searched at the venue's coords when Swiggy returns them'. The planner's dispatch always sends the group pin: `loc` is built once from lat/lng (maa/plan.py:195) and spread into every call, including search_restaurants_dineout (maa/plan.py:210). The search_restaurants tool spec has no venue argument. Nothing in the design or Next Steps step 4 changes this, so every search stays at the pin and distance is never 'known'.

**Remedy**

> Add a venueId argument to the planner's search_restaurants tool. Code resolves that venue's coords from the run's get_event_details/list_event_shows responses and falls back to the pin when there are none. Add this change to Next Steps step 4.

### R3-2 — feasibility

**Problem**

> checks.py has to parse facts 'keyed by those IDs', check that 'the showId belongs to the eventId', and know which search point each restaurant came from (for 'known' distance). The current corpus is a flat concatenated string (corpus_parts joined at maa/plan.py:192, 238). It records neither which call returned which ID nor the call's arguments (eventId, lat/lng). That structure is new work and isn't listed.

**Remedy**

> State that the planner records each tool call as a structured record (tool, args including lat/lng, parsed response via embedded_json). checks.py builds its ID→facts and parent-child maps (event→show, restaurant→slot, search point→restaurant) from those records. Add this to Next Steps step 4.

### R3-3 — completeness

**Problem**

> Check 1 binds only showId→eventId and itemId→restaurant. It doesn't require the slotId to come from a get_available_slots response for that restaurantId on `date`, the venueId to belong to the show/event, or the model-supplied reservationTime to equal the slot's time. Checks 2 and 3 run on the table time, so a model-written reservationTime could pass timing checks that the real slot fails.

**Remedy**

> Extend check 1: slotId must come from get_available_slots for that restaurantId and date, venueId must match the show's venue, and the table time used by checks 2-3 is read from the slot response (reject a reservationTime that differs).

### R3-4 — consistency

**Problem**

> Dinner-only plans are triggered when 'no show passes check 2's show test, or no event plan passes all checks'. Yet they 'may mix with event plans'. Under that trigger there is never a passing event plan to mix with.

**Remedy**

> Either change the trigger to 'fewer than 3 event plans pass' (fill the remaining slots with dinner-only plans), or drop the mixing sentence.

### R3-5 — feasibility

**Problem**

> The document doesn't say when the dinner-only search runs relative to the event attempt and its one retry. It also doesn't say whether it is a separate planner attempt and how it fits the 20/30 call caps and the 90 s deadline. If event planning uses the whole job budget, a dinner-only fallback may have no calls or time left.

**Remedy**

> Define the sequence (e.g., event attempt → retry → dinner-only attempt), and reserve a call and time budget for the dinner-only step within the 30-call and 90 s limits.

### R3-6 — consistency

**Problem**

> Headcount can exceed the chat members ('4 log (3 chat mein)'), and plans and slots are chosen for it. But RSVP eligibility is only the organizer + validated people, and party size = confirmed count. The friend outside the chat can never be confirmed, so the table is booked for 3 when the group said 4.

**Remedy**

> Add a way to count people outside the chat in the party size (e.g., an organizer '+1 guest' button on the RSVP), or state that the party size deliberately covers only chat members and show this on the Book prompt.

### R3-7 — completeness

**Problem**

> Now that extraction outputs statements rather than people[], 'validated people' is undefined, yet voting eligibility, RSVP eligibility, headcount and the per-person card all use it. It isn't stated whether it means every buffered human sender or only senders of kept statements. It also isn't stated whether a sender whose latest statement is not_coming is counted in the headcount, eligible to vote, or shown on the card.

**Remedy**

> Define validated people (e.g., distinct senders of kept statements) and state how not_coming affects headcount, vote/RSVP eligibility and the per-person ✓ row.

### R3-8 — completeness

**Problem**

> RSVP taps 'can be toggled until the organizer taps Book'. But the Book tap is queued, and the round stays BOOK_PENDING through the show-gone and slot-gone re-tap loops, so the inline RSVP handler has nothing that tells it Book was tapped. The count in the prompt ('Table for 3') can also go stale before the job reads it. Which party size gets booked is undefined.

**Remedy**

> Snapshot the confirmed count into the booking job at the Book tap (and show it in the confirmation). Either reject RSVP taps after the snapshot, or re-snapshot on each Book re-tap and edit the prompt when the count changes.

### R3-9 — completeness

**Problem**

> The buffer purges old rows only on insert, and /commands aren't inserted. In a chat that went quiet, /plan therefore feeds extraction messages older than 24 h, which contradicts 'pichle 24 ghante ki chat padhta hu' and can pull in a previous weekend's constraints.

**Remedy**

> Filter the buffer to the last 24 h (and 50 rows) when extraction reads it, or run the purge at /plan before reading.

### R3-10 — consistency

**Problem**

> The join notice promises 'Plan ki details 7 din baad delete', but the retention purge runs only lazily on each /plan. A group that never sends /plan again keeps its Constraints, statements, votes and RSVPs indefinitely. It is also unstated whether a /plan purges only its own chat's rounds or all chats'.

**Remedy**

### R3-11 — clarity

**Problem**

> The open-round rule lets any member replace a round 'idle > 30 min', but 'idle' is undefined (time since the last state transition, tap or message?). The RSVP stage has a 30 min deadline and people are buying tickets, so a round in RSVP or BOOK_PENDING can legitimately be idle past 30 min and any member could close it.

**Remedy**

> Define idle (e.g., no state transition, vote or RSVP tap for N min) and decide whether RSVP/BOOK_PENDING rounds need a longer threshold or the organizer's consent.

**Remedy**

### Design decisions (each auto-approved: recommended option)
- **DR1 Plan layout:** each plan is 4 fixed lines: title · show line · table line · cost + fit line. Misfits are named ("Priya: budget pata nahi"); everyone fitting collapses to "Sab fit ✓ (4/4)".
- **DR2 Message budget:** at most **4 new messages per round**: (1) Samjha, edited in place for the gap question; (2) progress, edited into the plans message; (3) organizer control message, edited through lock → guests → book; (4) RSVP, edited into the final card and pinned. Stale keyboards are removed on every stage change (editMessageReplyMarkup with an empty keyboard).
- **DR3 Organizer-only controls:** they live only in the organizer control message, which starts with "@<organizer>". A friend who taps one gets the toast "Yeh sirf @Harsh (organizer) dabaa sakta hai". The gap question and Samjha also @-mention the organizer.
- **DR4 Quiet friends can vote and RSVP (reopens CEO R3-7 voting eligibility):** any group member may vote and RSVP. Their first tap adds them to the round's people, shown as "kuch nahi bola". The lock threshold is "more than half of known people (validated + tappers)". Card fit rows still come only from what people said.
- **DR5 One Hinglish voice + full copy table** (below). Every bot string is Roman-script Hinglish, English never mixed mid-sentence. "Table for 3" becomes "3 logon ki table"; "Working on it…" becomes "Kar raha hu…".
- **DR6 Samjha marks assumptions:** facts from chat are plain. Defaults sit on one line starting "🤖 Maan liya:" (e.g. "budget kisi ne nahi bola → koi limit nahi").
- **DR7 State matrix** (below): empty chat, extraction progress, partial results, ended rounds.
- **DR8 Ticket-aware RSVP:** buttons [🎟 Ticket le liya] [🙋 Aa raha, ticket baaki] [❌ Nahi aa paunga], shown on 3 rows. Party size = ticket le liya + aa raha + guests. The guest buttons live in the organizer control message.
- **DR9 Vote buttons:** one per row, label "1 · <plan title ≤18 chars>… (votes)". Restaurant and venue names never appear in button labels.
- **DR10 Pin prompt:** "📍 Area batao: phone se 📎 → Location (desktop se nahi hota)". If the T1 probe finds that Swiggy's Scenes locations give coordinates for localities, `/area <locality>` also works as text; otherwise it's a pin only.
- **DR11 Time and money format:** "Sat 5 Oct · raat 10 baje" (never bare "10:00"); money "₹750"; approximate values "~₹750"; show end estimates "~raat 9:30".
- **DR12 Badlo:** after Badlo, the bot posts a force_reply message (selective, to the organizer): "@Harsh, kya galat hai? Isi message pe reply karo". The reply is appended to extraction.
- **DR13 Accessibility:** at most one emoji per line, used only as a line marker. Every ✓/✗/? has a word beside it ("veg ✓ haan", "budget ? pata nahi"). No information is carried by emoji alone.
- **DR14 Final card:** lists the date, show time + venue, table time + restaurant + party size, who's coming (names + guests), ~₹/head, a maps link for the restaurant (if Swiggy returns an address or coordinates), the ticket pointer, and who hasn't bought a ticket. The bot pins it (pinChatMessage; needs pin rights, otherwise it skips silently and logs).
- **DR15 Payoff first:** the final card leads with "🎉 Sat ka plan pakka!". TEST_ONLY is a one-line footer: "🧪 Test mode: table asli mein book nahi hui".
